## 1. Functional and Non-Functional Requirements

### 1.1 Functional Requirements (What the System Does)
Functional requirements describe the exact features and actions users can perform in the job portal.

#### A. Candidate Features
1. **Account Registration & Login:** Job seekers can register with their name, email, phone number, headline, summary, and experience level.
2. **Profile & Qualification Setup:**
   - **Education Management:** Add, view, and delete educational qualifications (college/university, degree, field of study, start date, graduation date, and GPA scaled from 0.0 to 10.0).
   - **Work Experience History:** Add past jobs, company names, job titles, duration, and roles performed.
   - **Resume Manager:** Upload and manage multiple resume versions (limited to a maximum of 5 resumes per candidate as per business constraint BC2). Mark any resume as the default.
   - **Skills Profile:** Select skills from a global skill bank and tag them with proficiency levels (Beginner, Intermediate, Expert) and years of experience.
   - **Job Preferences:** Set desired job title, expected salary, preferred work model (Remote, Hybrid, Onsite), and earliest available start date.
3. **Job Search & Filters:** Candidates can search active job listings by job title, location, employment type (Full-time, Part-time, Contract, Internship), and minimum salary.
4. **Job Application:**
   - Apply to jobs in one click using a selected resume version.
   - Answer mandatory screening questions set by the employer.
   - Duplicate prevention: The system automatically blocks submitting a second active application to the same job.
5. **Application Status Tracking:** Track live application stages (*Applied*, *Under Review*, *Shortlisted*, *Interviewing*, *Offered*, *Hired*, or *Rejected*).

#### B. Employer & Recruiter Features
1. **Company & Employer Account Registration:** Companies register their organization details (industry, website, headquarters location, company description) and select a subscription plan.
2. **Subscription Credit System:**
   - Every employer account is assigned credits based on their subscription tier (*Free: 5 credits, Standard: 25 credits, Premium: 100 credits, Enterprise: 500 credits*).
   - Posting a job automatically checks account verification status and deducts 1 credit.
3. **Job Posting Management:**
   - Create and publish job openings with title, description, location, employment type, seniority level, minimum salary, and maximum salary.
   - Add custom screening questions to evaluate applicants upfront.
   - Edit, close, or archive job postings.
4. **Applicant Tracking System (ATS):**
   - View all applicants for each job posting.
   - Inspect applicant resumes, education, skills, and answers to screening questions.
   - Move applicants through hiring stages (*Applied → Shortlisted → Interviewing → Offered → Hired / Rejected*).

#### C. Platform Operations & Admin Features
1. **Employer Verification Workflow:** Administrators review and approve/reject new employer accounts to keep the platform free from spam and fake jobs.
2. **Platform KPI Metrics:** Track real-time platform statistics (total registered candidates, active job posts, total applications submitted, and verified employers).
3. **Analytics Reports:**
   - Subscription revenue generated by each tier.
   - Top-paying jobs grouped by industry.
   - Identification of unfilled jobs that have not received any applications.
   - Average time-to-hire across departments.
4. **SQL Query Runner:** Built-in interactive interface to execute and inspect all 30 analytical and transactional queries from Lab 10A.

### 1.2 Non-Functional Requirements (How Well the System Performs)
Non-functional requirements describe the quality, performance, and reliability standards of the system.

1. **Performance & Speed:**
   - SQL queries and search filters return results in less than 200 milliseconds by indexing foreign keys and primary keys.
   - User interface updates instantly with reactive data re-fetching.
2. **Data Consistency & Integrity (ACID Compliance):**
   - All transactions (like job posting with credit deduction or application submission) run with full ACID guarantees in PostgreSQL.
   - Foreign key constraints ensure no orphan records exist (e.g., deleting a candidate cascades cleanly to their education and resume records).
   - Domain constraints prevent invalid data (e.g., GPA must be between 0.0 and 10.0; salary cannot be negative).
3. **Scalability & Normalization:**
   - The database is normalized up to Boyce-Codd Normal Form (BCNF) across 16 tables, eliminating insertion, deletion, and update anomalies.
4. **Usability & Simplicity:**
   - Clean, modern web user interface with simple dropdown menus for active candidates and employers, eliminating the need to manually memorize or type database IDs.
   - Visual badges and progress indicators make application stages obvious at a glance.
5. **Security & Role Separation:**
   - Strict separation between Candidate, Employer, and Admin portals so users can only perform actions permitted for their role.

### Plain-Language Summary of Entities & Connections:
- **`COMPANY` & `EMPLOYER`:** A company registers on the platform and has an employer account (`1-to-1`).
- **`EMPLOYER_USER`:** An employer account can have multiple recruiter/admin team members (`1-to-Many`).
- **`SUBSCRIPTION_PLAN`:** Employers choose a subscription plan that allocates job posting credits (`Many-to-1`).
- **`JOB_POSTING`:** Employers create job postings (`1-to-Many`).
- **`SCREENING_QUESTION`:** A job posting can include custom screening questions (`1-to-Many`).
- **`CANDIDATE`:** Job seekers who register on the portal.
- **Candidate Weak Entities:** A candidate owns their `EDUCATION`, `EMPLOYMENT_HISTORY`, `RESUME`, and `JOB_PREFERENCE` (`1-to-Many`).
- **`SKILL`:** Central skills catalog linked to candidates via `CANDIDATE_SKILL` and to jobs via `JOB_SKILL` (`Many-to-Many`).
- **`APPLICATION`:** Created when a candidate applies to a job posting (`Many-to-Many` bridge between Candidate and Job).
- **`APPLICATION_ANSWER`:** Stores the candidate's answers to the job's screening questions.

## 3. Final Relational Schema Diagram

Below is the logical relational model showing all 16 tables, primary keys (PK), foreign keys (FK), and relationship connections using Crow's Foot notation:

![Final Relational Diagram](report_assets/final_relational_diagram.png)

### Key Relational Mapping Rules Used:
1. **Strong Entities:** Tables with a simple single-attribute primary key (e.g., `CandidateID` in `CANDIDATE`, `CompanyID` in `COMPANY`, `PlanID` in `SUBSCRIPTION_PLAN`, `SkillID` in `SKILL`).
2. **Weak Entities:** Tables whose existence depends on a parent entity. The primary key includes the parent's primary key plus a local partial key:
   - `EDUCATION` $\rightarrow$ `{CandidateID, EducationID}`
   - `EMPLOYMENT_HISTORY` $\rightarrow$ `{CandidateID, HistoryID}`
   - `RESUME` $\rightarrow$ `{CandidateID, ResumeID}`
   - `JOB_PREFERENCE` $\rightarrow$ `{CandidateID, PrefID}`
   - `EMPLOYER_USER` $\rightarrow$ `{EmployerID, UserID}`
   - `SCREENING_QUESTION` $\rightarrow$ `{JobID, QuestionID}`
3. **Many-to-Many Junctions:**
   - `CANDIDATE_SKILL` $\rightarrow$ `{CandidateID, SkillID}`
   - `JOB_SKILL` $\rightarrow$ `{JobID, SkillID}`
   - `APPLICATION_ANSWER` $\rightarrow$ `{ApplicationID, JobID, QuestionID}`

## 4. Normalised Schema (BCNF)

The schema was refined step-by-step from 1NF to Boyce-Codd Normal Form (BCNF). In BCNF, for every functional dependency $X \rightarrow Y$, the determinant $X$ must be a superkey. This guarantees zero redundancy and no update, insertion, or deletion anomalies.

### Table-by-Table Normalized Relations:

1. **`COMPANY`**
   - **Columns:** ($\underline{\text{CompanyID}}$, Name, TradeName, Industry, Website, Logo, HQ_Location, Description)
   - **Primary Key:** `CompanyID`

2. **`SUBSCRIPTION_PLAN`**
   - **Columns:** ($\underline{\text{PlanID}}$, TierName, PostingLimit, Credits, Price)
   - **Primary Key:** `PlanID`

3. **`EMPLOYER`**
   - **Columns:** ($\underline{\text{EmployerID}}$, $\text{CompanyID}^*$, $\text{PlanID}^*$, Email, Phone, VerificationStatus, CreditsRemaining)
   - **Primary Key:** `EmployerID`
   - **Foreign Keys:** `CompanyID` references `COMPANY`, `PlanID` references `SUBSCRIPTION_PLAN`

4. **`EMPLOYER_USER`**
   - **Columns:** ($\underline{\text{EmployerID}^*}, \underline{\text{UserID}}$, Name, Email, Role)
   - **Primary Key:** Composite {`EmployerID`, `UserID`}
   - **Foreign Key:** `EmployerID` references `EMPLOYER`

5. **`CANDIDATE`**
   - **Columns:** ($\underline{\text{CandidateID}}$, Name, Email, Phone, Headline, Summary, Location, ExperienceLevel, ProfileVisibility)
   - **Primary Key:** `CandidateID`

6. **`EDUCATION`**
   - **Columns:** ($\underline{\text{CandidateID}^*}, \underline{\text{EducationID}}$, Institution, Degree, FieldOfStudy, StartDate, EndDate, GPA)
   - **Primary Key:** Composite {`CandidateID`, `EducationID`}
   - **Foreign Key:** `CandidateID` references `CANDIDATE`

7. **`EMPLOYMENT_HISTORY`**
   - **Columns:** ($\underline{\text{CandidateID}^*}, \underline{\text{HistoryID}}$, PreviousCompanyName, JobTitle, StartDate, EndDate, Description)
   - **Primary Key:** Composite {`CandidateID`, `HistoryID`}
   - **Foreign Key:** `CandidateID` references `CANDIDATE`

8. **`RESUME`**
   - **Columns:** ($\underline{\text{CandidateID}^*}, \underline{\text{ResumeID}}$, VersionName, FilePath, IsDefault)
   - **Primary Key:** Composite {`CandidateID`, `ResumeID`}
   - **Foreign Key:** `CandidateID` references `CANDIDATE`

9. **`JOB_PREFERENCE`**
   - **Columns:** ($\underline{\text{CandidateID}^*}, \underline{\text{PrefID}}$, TargetTitle, ExpectedSalary, PreferredWorkModel, AvailabilityDate)
   - **Primary Key:** Composite {`CandidateID`, `PrefID`}
   - **Foreign Key:** `CandidateID` references `CANDIDATE`

10. **`SKILL`**
    - **Columns:** ($\underline{\text{SkillID}}$, SkillName, Category)
    - **Primary Key:** `SkillID`

11. **`CANDIDATE_SKILL`**
    - **Columns:** ($\underline{\text{CandidateID}^*}, \underline{\text{SkillID}^*}$, ProficiencyLevel, YearsOfExperience)
    - **Primary Key:** Composite {`CandidateID`, `SkillID`}
    - **Foreign Keys:** `CandidateID` references `CANDIDATE`, `SkillID` references `SKILL`

12. **`JOB_POSTING`**
    - **Columns:** ($\underline{\text{JobID}}$, $\text{EmployerID}^*$, Title, Description, Location, EmploymentType, SeniorityLevel, SalaryMin, SalaryMax, PostDate, ExpiryDate, Status)
    - **Primary Key:** `JobID`
    - **Foreign Key:** `EmployerID` references `EMPLOYER`

13. **`JOB_SKILL`**
    - **Columns:** ($\underline{\text{JobID}^*}, \underline{\text{SkillID}^*}$, ProficiencyLevel, IsMandatory)
    - **Primary Key:** Composite {`JobID`, `SkillID`}
    - **Foreign Keys:** `JobID` references `JOB_POSTING`, `SkillID` references `SKILL`

14. **`SCREENING_QUESTION`**
    - **Columns:** ($\underline{\text{JobID}^*}, \underline{\text{QuestionID}}$, QuestionText, QuestionType)
    - **Primary Key:** Composite {`JobID`, `QuestionID`}
    - **Foreign Key:** `JobID` references `JOB_POSTING`

15. **`APPLICATION`**
    - **Columns:** ($\underline{\text{ApplicationID}}$, $\text{CandidateID}^*$, $\text{JobID}^*$, $\text{ResumeID}^*$, Timestamp, Stage, IsDraft)
    - **Primary Key:** `ApplicationID`
    - **Foreign Keys:** `CandidateID` references `CANDIDATE`, `JobID` references `JOB_POSTING`, `{CandidateID, ResumeID}` references `RESUME`

16. **`APPLICATION_ANSWER`**
    - **Columns:** ($\underline{\text{ApplicationID}^*}, \underline{\text{JobID}^*}, \underline{\text{QuestionID}^*}$, AnswerText, AnsweredAt)
    - **Primary Key:** Composite {`ApplicationID`, `JobID`, `QuestionID`}
    - **Foreign Keys:** `ApplicationID` references `APPLICATION`, `{JobID, QuestionID}` references `SCREENING_QUESTION`

## 6. How and Where AI Was Used in This Project

AI was used as an interactive pair-programming, analysis, and verification assistant throughout the project lifecycle:

1. **Schema Refinement & Normalization (Labs 6 to 9):**
   - AI helped critique initial Entity-Relationship drafts, identifying hidden transitive dependencies.
   - For example, separating `COMPANY` from `EMPLOYER` so that organization profile details are not duplicated when multiple recruiters or accounts exist, ensuring strict adherence to BCNF.

2. **Realistic Seed Data Generation:**
   - Generating 100 realistic, coherent records per table (1,600 total tuples) with valid foreign key references, realistic Indian job titles, GPA distributions, and salary bands for PostgreSQL testing.

3. **Complex SQL Query Formulation (Lab 10A):**
   - Assisting in structuring advanced analytical queries involving window functions (e.g., `DENSE_RANK() OVER (PARTITION BY Industry ORDER BY SalaryMax DESC)`), time-to-hire interval extractions, and PL/pgSQL stored procedures.

4. **GUI Development & Rapid Prototyping:**
   - Drafting responsive Streamlit layouts, tab architectures, and custom CSS styling to create a clean, professional dark-mode design.
   - Implementing defensive data-fetching helpers (`safe_val`) to handle null values gracefully without throwing Python exceptions.

5. **Code Review, Bug Fixing & Verification:**
   - Identifying and resolving syntax edge cases, such as adding the required `$$ LANGUAGE plpgsql;` terminator to Query 30's trigger function and fixing parameter signatures so all 30 queries execute cleanly with zero errors.
